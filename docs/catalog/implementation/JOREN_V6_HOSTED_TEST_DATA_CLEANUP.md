# Synthetic write manifest and cleanup

The private manifest records the exact run ID, two Auth subjects, two opaque athlete IDs, backend mutation requests/responses, returned record IDs and primary-key inventories. Auth creation attempts are journaled before dispatch; Auth HTTP outcomes and the subjects of all session operations are recorded. Transient internal Auth session rows from intermediate login attempts were not independently enumerated before revocation; subject-wide logout and the final exact-owner inventory establish their cleanup. The manifest is ignored by Git and restricted to the owner and SYSTEM. Committed evidence contains labels, status codes, table counts and fingerprints, never test passwords, access/refresh tokens, token payloads, emails, athlete IDs or private physiological responses.

Hosted writes were limited to two confirmed administrative Auth creations; real logins, refreshes and logouts; each test athlete's normal onboarding/history/goal/zone confirmations; check-ins; actual historical plan generation and separate confirmation; two supported synthetic activities with idempotent retries; two unfinished-workout moves; and A's historical swipe draft/choices/pending submission. Foreign and stale requests were rejected. The exact resulting per-table counts are in [cleanup evidence](hosted-auth-20261114/cleanup.json); descendants such as plan revisions, workloads and zone versions were created only by existing reviewed procedures.

Before deletion, read-only primary-key inventory was filtered exclusively to the two manifested Auth subjects and opaque athlete IDs. Foreign keys confirmed `auth.users -> private.athlete_identity_map -> owned records` cascading deletion, and Auth/DB callback settings were reviewed. Global logout revoked both sessions before deletion. Auth admin GET revalidated each exact subject, canonically lowercased synthetic email and run metadata. The first attempt stopped without deleting because GoTrue had lowercased the generated email. After exact identity/canonicalization checks, supported admin DELETE succeeded for each; subsequent GET returned 404. There was no SQL DELETE, wildcard cleanup, trigger disabling or permission change.

After deletion, **all 61 inspected owner-key tables had zero matching test rows**, including Auth users/identities/sessions/refresh tokens, opaque mappings, public plans/activities/check-ins/zone data and private plan/workout loads. The separate exact-actor Auth security audit query found zero retained entries; this does not claim that platform access logs were erased. Infrastructure logs remain subject to Supabase's normal retention.

After both genuine original tokens passed the real-time expiry rejection check, synthetic passwords, sessions and tokens were removed from the private manifest. The temporary complete Auth-configuration response was also removed after its before/after equality check; only its fingerprint and safe settings remain. Existing owner credential files were untouched. The remaining private identity/inventory manifest supports owner audit, without credentials. Ordinary accepted historical evidence is retained separately. No real athlete record was targeted, read or modified. This conclusion is supported by exact-ID query/mutation scoping and unchanged schema/configuration, not by copying unrelated private athlete rows for comparison.
