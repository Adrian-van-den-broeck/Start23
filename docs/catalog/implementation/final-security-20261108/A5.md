## Exact root cause

`private.assert_current_planning_eligibility` is invoked by revision creation
before attachment. Its current implementation originates in the R4/R5 migration,
with satisfied-step rules tightened by R6. The original fixture supplies only an
`in_progress` operational profile with a confirmed manual timezone. The actual
diagnostic query returns **only `timezone`** as satisfied on both schemas.

Missing data and relationships are:

- A physiology profile keyed by the **opaque athlete ID**, with date of birth
  and resting heart rate. The operational profile and identity map already exist;
  the identity mapping itself is not defective.
- Explicit heart-rate-monitor confirmation on the operational profile.
- All three discipline history rows with non-null previous-month minutes and
  `phase-13-joren-ruleset-1` provenance. Synthetic zero is explicit zero history.
- An active structured race goal with required discipline, name, date and target
  time. The synthetic recovery scenario remains a run goal.
- An active run zone profile, the race-required discipline. Setup intent alone
  does not satisfy current eligibility. The correction also creates the normal
  synthetic metric and five boundaries, following the existing fixtures.
- A completed onboarding session at `phase-14-onboarding-v2` /
  `phase-13-joren-ruleset-1`, linked to a non-cancelled initial-plan request with
  the same opaque owner and version provenance.

The new fixture seeds those ordinary synthetic inputs as the disposable database
owner, then **sets the existing authenticated owner role and calls
`complete_current_onboarding(expected_revision)`**. It does not insert fake
completion/session records, alter eligibility, disable constraints, add grants,
or create a planning bypass. The normal RPC creates the linked session/request,
one completion record and completed profile. All six required steps then pass.
The check-in IDs, weeks, payload restrictions, trigger, recovery states and
original assertions remain the same. All fixture changes roll back with the suite.

The original owner relationship remains correct: `auth_user_id` differs from
the opaque `athlete_id`; the physiology row uses the latter. Legacy public
inputs use the existing owner-sync triggers. [Observed prerequisites](a5-prerequisites.json)
record both schemas before and after correction, including the exact owner link.

After onboarding completion, the original `input_fingerprint=repeat('a',64)`
hits `plan_revisions_fingerprints_valid`. That historical constraint requires
**32 hexadecimal characters for the input fingerprint**, and 64 for generation.
Changing only the synthetic input fingerprint to `repeat('a',32)` reaches the
intended PT409 attachment trigger. Generation fingerprints remain 64 characters.
This is test data conforming to the established contract, not a schema change.
